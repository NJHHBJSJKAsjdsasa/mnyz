# 实时 PvPvE · 跨区多活 · 微服务：目标架构（v3）

> 写给下一次会话 / 架构评审：本文是**目标架构与演进路线**，不含实现代码。
> 前置：`docs/SERVER_PG_DESIGN.md`（v2，单区域生产化）。v3 是 v2 之上的升级，不是替换。
> 最后更新：2026-10-25

---

## 0. 结论先行

1. **三件事要分开排期，不能一起上**。它们对一致性的要求互相冲突：实时要求「快且可丢」，多活要求「分区可写」，微服务要求「跨服务一致」。同时开工会得到一个既卡又乱、且无法回滚的系统。
2. **推荐顺序**：单区域生产化（v2 M0–M6）→ 抽出 `battle` 实时服务（单区域）→ 服务拆分补全 → 玩家分片的跨区多活 → 全局能力（排行/社交/活动）。
3. **三个反直觉但必须接受的结论**：
   - **钱包绝不能多主**。多活是「玩家分片」，不是「同一钱包在两地区都能写」。
   - **战斗服务不该用 Python**。20Hz 权威模拟 + 每节点数十实例，Python 的 GIL 与 GC 会直接变成手感问题。建议 Go（或 Rust），与现有 Flask 通过 gRPC/事件解耦。
   - **微服务不是目标，边界才是**。现在 26 个前端系统 + 单 Flask 进程里没有稳定边界，直接拆服务只会把「隐式耦合」变成「分布式隐式耦合」。
4. 规模与周期（4–6 人）：**9–14 个月**到「三地区、实时战斗、8 个服务」的稳态。任何「三个月做完」的承诺都不成立。

## 1. 需求拆解与冲突矩阵

| 需求 | 本质要求 | 与其它两者的冲突 | 解决方向 |
|---|---|---|---|
| 实时 PvPvE | 权威模拟、低延迟、可丢帧、会话态 | 与多活冲突：跨区对战必然 >100ms；与微服务冲突：战斗结果需要强一致的奖励发放 | 战斗实例**区域内**封闭运行，结果走事件 + saga 结算 |
| 跨区多活 | 低延迟接入、区域故障可切换、容量叠加 | 与经济强一致冲突：跨区双写钱包必然对账不平 | **玩家分片单写**（home region），跨区只做读与战斗 |
| 微服务 | 独立部署、独立数据、故障隔离 | 与实时冲突：链路过长会增加 p99；与多活冲突：服务×区域矩阵爆炸 | 只拆 8 个有界上下文，内部 gRPC，外部网关聚合 |

**优先级**：正确性 > 可运维性 > 延迟 > 开发速度。实时战斗是唯一允许「丢状态换延迟」的地方，经济绝不允许。

### 2.1 服务清单与数据所有权（一个数据只能有一个写者）

| 服务 | 有界上下文 | 拥有的数据（写） | 只读自 |
|---|---|---|---|
| `gateway-bff` | 接入、鉴权校验、聚合、WS 升级 | 无（无状态） | 全部下游 |
| `identity` | 账号、会话、令牌、区域归属 | `accounts`, `sessions`, `identity_directory` | — |
| `player` | 角色档案、船、模块、空间站、舰队、科技、图鉴 | `players`, `ships`, `ship_modules`, `stations`, `fleet_ships`, `player_progress` | `economy`（余额快照） |
| `economy` | 钱包、账本、市场、合同、生产、券 | `wallets`, `ledger_*`, `market_*`, `contracts`, `trade_orders` | `player`（等级/模块） |
| `universe` | 星系/行星生成与缓存、情报 | `universe_cache.*`, `intel_reports` | — |
| `battle` | 实时 PvPvE 实例、匹配、战报 | `battle_sessions`, `battle_results`（**不含钱包**） | `player` 快照、`economy` 战利品表 |
| `social` | NPC、势力、联盟、聊天、在线状态 | `npc_*`, `faction_*`, `alliances`, `presence` | `player` 摘要 |
| `platform` | 通知、埋点、运营、定时任务 | `outbox`, `jobs`, `audit` | 全部（只写自己的表） |

**硬规则**：`battle` 不得直连 `wallets`；`gateway` 不得直连任何数据库；`universe` 不得写玩家数据。

## 3. 实时 PvPvE 设计

### 3.1 玩法边界（先定死，避免无限扩张）

| 维度 | 取值 | 理由 |
|---|---|---|
| 单场人数 | 2–8 人 + NPC 波次 | 与现有「舰队 3 艘」的规模匹配；8 人是带宽与平衡的甜点 |
| 单场时长 | 3–5 分钟，硬上限 8 分钟 | 移动端友好，方便分片回收 |
| 模式 | PvPvE 撤离制：进场 → 打 NPC 收集 → 可互相攻击 → 到达撤离点结算 | 复用现有「货舱 + 损失 5% 货物 + hull −20」的经济语义 |
| 死亡惩罚 | 货舱损失 50%（PvE 失败仍是 5%）+ hull −20，不掉改装等级 | PvP 需要更高风险，但不能摧毁长期进度 |
| 跨区 | 默认同区匹配；仅当双方延迟预算都接受时才跨区（>80ms 不撮合） | 跨区实时战斗体验不可控 |
| NPC | 沿用现有确定性生成（seed = battle_id），阵营/强度按玩家舰队战力锚定 | 与现有 K1/K5 数值体系一致 |

> **与行星归属的关系**：实时战斗**不**直接决定行星所有权。共享行星的争夺采用「异步确定性攻城推演」：宣战后 12 小时，服务端用 `seed = hash(siege_id)` 与双方舰队快照推演并单事务结算（见 `SERVER_PG_DESIGN.md` §7.12）。实时 PvPvE 只发生在中立匹配实例中，避免跨区实时攻城在延迟与一致性上都不可交付。

### 3.2 网络与协议

| 项 | 选型 | 说明 |
|---|---|---|
| 传输 | WebTransport（HTTP/3 QUIC，不可靠数据报）优先；WebSocket 兜底 | UDP 语义避免 TCP 队头阻塞；WS 兜底保证兼容 |
| 编码 | Protobuf（二进制，schema 版本化） | JSON 在 20Hz 下体积不可接受 |
| 上行 | 客户端 30Hz 输入：`seq, tick_hint, thrust, turn, fire, shield, evade, target` | 单包 ≤ 24B |
| 下行 | 服务端 10Hz 快照：`tick, acked_seq, entities[]`（位置/速度/HP/护盾/状态位） | 8 实体约 480B/包 → 4.8KB/s/客户端 |
| 事件 | 低频可靠通道：击杀、拾取、波次、撤离点开启 | 可靠传输，独立于快照流 |
| 时钟 | 服务端 tick 单调递增；客户端维护 `server_time_offset`（RTT/2 平滑） | 不用绝对时间戳做判定 |

带宽估算：8 人场，单客户端下行 ~5KB/s、上行 ~1KB/s。1000 并发场 ≈ 6MB/s 出向，普通节点即可承载。

### 3.3 权威模拟

- 服务端固定步长 `dt = 50ms`（20Hz），tick 内按输入队列顺序应用，超时未达的输入按「保持上一帧」处理。
- 客户端本地预测自己的船（相同物理参数、相同步长），维护未确认输入队列；收到快照后：
  - 若 `acked_seq` 与预测一致 → 丢弃已确认输入，继续预测；
  - 不一致 → 回滚到快照状态，重放未确认输入（rollback reconciliation）。
- 其他实体做**快照插值**（渲染延迟 100ms），不预测。
- 物理简化：2D 平面（现有战斗就是平面化数值对抗）+ 有限转向率，避免 3D 弹道带来的一致性成本。

### 3.4 命中与延迟补偿

- 命中判定全在服务端；对射击类动作做**回溯补偿**：按客户端 `server_time_offset` 回退最多 200ms 的世界快照做射线/距离判定。
- 反作弊红线：客户端只发意图，从不发位置/伤害/命中结果；服务端校验推力上限、转向速率、射速、护盾冷却。

### 3.5 匹配与分区

- 输入：MMR（由现有排行榜 + 近期战绩派生）、舰队战力、区域、延迟预算、组队。
- 队列：Redis Sorted Set，按 MMR 分桶（±100 起步，每 10 秒放宽 50），硬上限 60 秒。
- 组队：2–4 人小队允许 MMR 取加权均值，禁止 4 人打散人。
- 分区：`region` 作为队列 key 前缀；跨区匹配需双方 `accept_cross_region=true`。

### 3.6 实例调度

- Kubernetes + **Agones**（GameServerFleet）：预热池 10%，按队列长度 HPA（每实例 8 人）。
- 分配流程：matchmaker 选出 8 人 → 向 Agones 申请 GameServer → 返回 `ws://game-{id}.battle.{region}.atlas/` → 客户端连接（带一次性 token，60 秒有效）。
- 回收：战斗结束 / 8 分钟 / 全员断线 30 秒 → 销毁；实例不跨场复用（避免状态残留）。

### 3.7 与经济系统的边界（最关键）

```
battle 开始                      battle 结束
──────────                       ──────────
economy: reserve(entry_fee)      battle → Kafka: battle.result
   （账本记「冻结」分录）            │
battle: 拿到快照 + 冻结凭证         ├─▶ economy: 消费（幂等键 = battle_id）
                                  │      · 发放战利品（账本）
                                  │      · 扣/退入场费
                                  │      · 扣 hull、损失货舱
                                  └─▶ player: 更新战绩/MMR
                                  平台: 写审计
```

- 入场费在开战前用**冻结**（两笔分录：玩家钱包 −x、系统冻结账户 +x），结束按结果结算，避免「开局扣钱后崩溃」两头空。
- 奖励发放必须幂等（`battle_id` 作为幂等键），战斗服务重启/重投事件不会双发。
- 若战斗实例崩溃：`battle.result` 带 `void=true`，economy 全额解冻，不扣惩罚。

### 3.8 反作弊

| 面 | 措施 |
|---|---|
| 客户端 | 只发意图；输入频率封顶（>45Hz 丢弃）；非法枚举值拒绝 |
| 服务端 | 全量权威；每 tick 校验位移/速度/冷却；异常累积触发踢出 |
| 统计 | 命中率/胜率/收益的 z-score 检测，超阈值进人工复核队列 |
| 对抗 | 战斗全程可回放（输入 + 快照摘要），支持举报复核 |
| 经济 | 奖励由 economy 侧二次校验（收益上限表），战斗服务无权直接加钱 |

### 3.9 断线与崩溃

- 断线 30 秒内可重连（一次性 resume token，服务端保留实体与输入缓冲）。
- 超时未回：视作撤离失败（保留 50% 货舱，hull −20），不额外惩罚。
- 实例崩溃：该场 `void`，全员解冻、无惩罚、MMR 不计。

### 3.10 技术选型（必须与现有 Python 栈分离）

| 方案 | 结论 |
|---|---|
| Python asyncio | 20Hz × 数十实例 + GC 抖动 → 手感不稳；GIL 下难以横向提高单机密度。**仅用于 PoC** |
| **Go**（推荐） | 单节点可跑 100+ 场；goroutine per battle；生态成熟（Agones SDK 有官方支持） |
| Rust | 性能更好但迭代慢；团队若无 Rust 经验不建议 |

集成方式：`battle` 作为独立服务暴露 gRPC（给 gateway 查战报/给 economy 发事件），不 import 现有 Python 代码；共享的只有 protobuf 事件契约与配置表。

## 4. 跨区多活

### 4.1 核心原则：玩家分片单写

- 每个 `player` 有且只有一个 `home_region`（注册时按延迟 + 配额分配，后续可迁移）。
- **该玩家的所有写操作只在 home region 执行**。其他区域只提供：只读档案、排行榜、社交读、战斗实例。
- 这样「多活」的含义是：多区域同时**承载各自玩家的读写与战斗**，而不是同一份钱包数据两地可写。
- 直接否掉：多主 Postgres、Galera、跨区 2PC、跨区同步写——延迟与故障域都不可接受。

### 4.2 区域归属

| 项 | 方案 |
|---|---|
| 分配 | 注册时测量 3 个区域 RTT（`/ping/{region}` 小端点），取最低延迟且未超配额的 |
| 存储 | `identity_directory(account_id, player_id, home_region, assigned_at, migrated_at)`，全局控制面唯一写者 |
| 客户端 | 登录后拿到 `home_region` 与 `api_base`，**后续所有请求只打本区**（DNS 也指向本区） |
| 迁移 | 运维流程（见 4.6），客户端无需改代码 |

### 4.3 读写路径

| 操作 | 路径 |
|---|---|
| 玩家状态读写 | 本区 `player`/`economy` 服务 + 本区 PG |
| 排行榜 | 本区 Redis 缓存 ← 全局汇总任务（每 5 分钟从各区拉聚合值） |
| 好友/联盟 | `social` 服务：成员关系存本区，跨区成员通过事件同步（最终一致，秒级） |
| 跨区观战/邀请 | 只读快照 + 延迟提示；不允许跨区同场（>80ms 拒绝） |
| 全局唯一性（昵称） | 全局控制面校验 + 各区缓存 |

### 4.4 数据复制

| 数据 | 方式 | 目标 |
|---|---|---|
| 玩家/经济数据 | 区内：PG 主 + 同区另一 AZ 同步副本；跨区：异步流复制（只读、灾备用） | 区内 RPO=0，跨区 RPO ≤ 1 分钟 |
| 参考数据（宇宙种子、模块定义、模板） | 逻辑复制，带 `data_version`，各区只读 | 版本不一致即告警 |
| 事件 | Kafka 区域集群 + MirrorMaker（单向或双向按 topic） | 跨区事件延迟 < 3s |
| 缓存 | 各区独立 Redis，不做跨区同步 | 竞态仅影响展示 |

### 4.5 跨区一致性（只允许 saga）

三个典型流程：

1. **PvPvE 战斗**（同区闭环，天然简单）：入场冻结 → 战斗 → 结果事件 → 本区结算。
2. **跨区 Gift/交易**（低频）：A 区扣款（冻结）→ 事件 → B 区入账 → 回执 → A 区解冻。失败则补偿退回。
3. **Home 迁移**（运维级）：见 4.6。

禁止：跨区同步调用链（`A → B → C` 串行）、跨区分布式事务、跨区共享表。

### 4.6 Home 迁移流程

1. 入口：玩家请求迁移 / 运维按容量调度。
2. 冻结：`identity` 写「迁移锁」，本区拒绝该玩家写入（HTTP 409 `migrating`），客户端进入只读。
3. 快照：源区导出该玩家全部行（按 `player_id` 跨表，约 100 行 / 200 KB）。
4. 装载：目标区导入（事务内，幂等键 `migration_id`）。
5. 追平：源区 WAL 增量 → 目标区回放（或逻辑复制 slot 追平）。
6. 切目录：更新 `identity_directory.home_region`，刷新 DNS/网关缓存。
7. 解冻：目标区开放写；源区清理迁移标记，保留 7 天只读备份。
8. 目标：冻结窗口 < 30 秒（正常 < 10 秒），迁移失败自动回滚到源区。

### 4.7 故障与分区

| 场景 | 行为 |
|---|---|
| 单 AZ 故障 | 同区同步副本提升（RPO 0），网关重连；用户基本无感 |
| 整区故障 | 提升该区跨区异步副本（RPO ≤ 1 分钟）→ 更新 DNS/路由 → 客户端重连（**该区玩家短暂不可写**）；其他区不受影响 |
| 全局控制面故障 | 各区用缓存继续服务（身份/路由缓存 TTL 10 分钟）；迁移与注册暂停 |
| 跨区网络抖动 | 只影响跨区社交/排行；战斗同区不受影响 |
| 脑裂 | 由于「钱包单写」，不存在双写；只需保证 `identity_directory` 只有一个写者（单区 + 选主） |

### 4.8 跨区成本

| 项 | 估算（三区、每区 staging 规模） |
|---|---|
| 计算 | 每区 4×4C8G app + 2× battle 节点 ≈ $600/月/区 |
| 数据库 | 主 4C16G + 副本 ≈ $400/月/区 |
| 网络 | 跨区复制与镜像 ≈ $100–300/月 |
| 合计 | staging ≈ $1.5–2k/月；生产（10k DAU）≈ $4–8k/月 |

## 5. 微服务化

### 5.1 拆分边界（只拆 8 个，不再多）

见 2.1 服务清单。判断标准：**是否有独立的数据所有权 + 独立的伸缩曲线 + 独立的故障域**。不满足就不拆（例如「通知」并入 `platform`，不单独成服务）。

### 5.2 通信

| 场景 | 方式 | 约束 |
|---|---|---|
| 客户端 → 后端 | REST（BFF 聚合）+ WebSocket/WebTransport（战斗） | BFF 只做聚合与鉴权，不写库 |
| 服务间同步 | gRPC（protobuf、deadline 200ms、重试仅幂等接口） | 禁止同步链 > 2 跳 |
| 服务间异步 | Kafka（事件、outbox 中继） | 至少一次 + 消费端幂等 |
| 战斗 ↔ 其他 | gRPC 拉快照；结果走 Kafka | 战斗不参与同步写 |

### 5.3 事件目录（schema 演进只增字段）

| 事件 | 生产者 | 消费者 | 关键载荷 |
|---|---|---|---|
| `economy.transaction_posted` | economy | 分析、风控 | `tx_id, player_id, kind, entries[]` |
| `battle.result` | battle | economy, player, platform | `battle_id, players[], outcome, loot[], void` |
| `market.rolled` | economy | platform, universe | `planet_key, game_day, quotes[]` |
| `contract.completed` | economy | platform, social | `contract_id, player_id, reward` |
| `player.progressed` | player | social, platform | `player_id, level, techs[]` |
| `alliance.changed` | social | economy（成员加成）、platform | `alliance_id, members[]` |
| `home.migrated` | identity | 全部 | `player_id, from, to, migration_id` |

版本化：事件带 `schema_version`；注册中心（Confluent Schema Registry 或自建）拒绝破坏性变更。

### 5.4 典型分布式流程（saga）

**PvPvE 结算**（最常见的跨服务流程）：

```
battle        ── battle.result ──▶ economy
economy       ① 幂等检查(battle_id) ② 发放战利品(账本) ③ 结算入场费 ④ 发 economy.settled
player        ◀── economy.settled ── 更新战绩/MMR/图鉴
platform      ◀── economy.settled ── 埋点与审计
失败处理：economy 消费失败 → 重试 3 次（指数退避）→ DLQ → 告警 + 人工重放工具
```

**跨区 Gift**：A 区冻结 → `gift.created` → B 区入账 → `gift.completed` → A 区解冻；超时 5 分钟未完成则自动补偿退回。

### 5.5 服务治理

| 项 | 方案 |
|---|---|
| 服务发现 | Kubernetes Service + gRPC DNS；不引入额外注册中心 |
| 传输安全 | mTLS（mesh 或 SDK 内建），证书轮换 24h |
| 超时/重试 | 全链路 deadline（BFF 1s、服务间 200ms）；重试仅对幂等 GET/查询 |
| 熔断/隔离 | 按下游依赖熔断（50% 错误 10s 窗口）；线程/连接池隔离 |
| 限流 | 网关按 token + 路由；服务内按关键资源（战斗实例数、账本写入） |
| 降级 | 排行/社交/情报可降级为缓存或隐藏；**经济与战斗不可降级** |
| 发布 | 金丝雀 5% → 25% → 100%，按错误率与 p95 自动回滚；DB 迁移必须向后兼容（先加列后用，先双写后切读） |

### 5.6 可观测（跨服务）

- `trace_id` 从网关生成，贯穿 REST → gRPC → Kafka（消息头传递）→ 战斗内 tick 日志。
- 每服务四块看板：RED、依赖、DB/队列、业务指标。
- 战斗额外指标：tick 超时率、平均 RTT、回滚次数、异常输入率。
- 端到端 SLI：`登录→进战→结算` 的成功率与 p95（目标 > 99%，p95 < 3s 不含战斗时长）。

### 5.7 仓库与团队

- **Monorepo**（服务边界靠目录与 CI 约束，不靠仓库拆分），因为共享 protobuf 与部署脚本；每个服务独立镜像与独立部署流水线。
- 团队划分（4–6 人）：平台/基建 1（k8s、PG、Kafka、可观测）、经济后端 1、玩家后端 1、战斗后端 1（Go）、前端 1、架构/负责人 1。

## 7. 验收与测试

| 类型 | 手段 | 阈值 |
|---|---|---|
| 战斗负载 | 机器人客户端（Go），1000 并发场 × 5 分钟 | tick 超时 < 0.1%，p99 RTT < 120ms（同区） |

| 区域故障 | 强杀整区 | 15 分钟内恢复，玩家数据 RPO ≤ 1 分钟 |
| 服务故障 | 逐个杀掉 8 个服务 | 其余功能可用或明确降级，无雪崩 |
| 迁移 | 100 个玩家 home 迁移 | 冻结 < 30s，迁移后账本对账 0 |

| 契约 | protobuf/Kafka schema 兼容性检查进 CI | 破坏性变更直接失败 |

## 8. 风险与「不要做」

| 风险 | 影响 | 缓解 |
|---|---|---|
| 实时战斗与现有「纯前端确定性」的设计哲学冲突 | 概念撕裂、两套逻辑 | 战斗只在服务端；现有 K1 单机战斗保留为「离线遭遇」，二者用同一套数值表 |
| 多活被误做成「钱包多主」 | 对账永远不平 | 玩家分片单写，写死在架构与评审清单里 |
| 服务拆得过细 | 运维成本爆炸、p99 上升 | 只拆 8 个；同步链 ≤ 2 跳 |
| 战斗用 Python 硬扛 | 手感差、密度低 | 战斗服务用 Go；Python 只做编排 |
| 跨区战斗滥用 | 体验崩坏 | 延迟预算硬门槛（>80ms 不撮合） |
| 迁移窗口过长 | 玩家流失 | 分片迁移 + 灰度 + 只读兜底 |
| 微服务先行、边界未稳 | 分布式隐式耦合 | 先 P0 完成权威化，再拆服务 |
| P2P 与中心服务定位冲突 | 双套身份体系 | 明确：中心服务是「云存档 + 竞技」权威；P2P 仍是「联邦宇宙」可选能力，不参与战斗结算 |

**明确不做**：分布式事务（2PC/XA）、跨区同步写、共享数据库的多服务、战斗服务直连钱包、用 CRDT 解决经济一致性。
